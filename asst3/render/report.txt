write-up:

    I chose to parallelize over pixels first. If we parallelize over circles first, 
    it will require a lot of communication (synchronization) between threads to ensure 
    the correctness of the code (to preserve circle order), which will cost a lot of time.

    For the execution configuration, I chose THREADS_PER_BLOCK = 256 (a healthy number) 
    with blockDim(16, 16). This means each block contains 256 threads, with each thread 
    responsible for rendering exactly one pixel.

    Note that every block has to check all circles (whether they need to be rendered) 
    and then render them. So I allocated a shared memory array to store the result 
    of the checking (a flag array, where all threads check together). I also chose a good 
    number of circles to be checked per round considering the shared memory size of the RTX 4090.


    Then we have to deal with the flag array.

    A simple way is to let every thread use a loop to iterate through the entire flag array 
    to check which circles need to be rendered, which is my first implementation. 
    This resulted in terrible performance. Since most circles in a large dataset do not intersect 
    a given 16x16 block, the threads wasted millions of cycles evaluating empty flags.

    Then I let thread 0 pick out the circles that needed to be rendered from the flag array 
    and write them to a new array (valid_circles) sequentially. Then all threads will only 
    iterate through the valid_circles array. This is my second implementation, and the 
    performance is better but still not good enough.

    After reconsidering the whole implementation, I was inspired by part 2 of this assignment 
    and implemented a scan algorithm to convert the flag array to the valid_circles array. 
    This is my final implementation, and the performance is perfect.


    There are some other optimizations I did:
    * Allocated a float4 pixelData for each thread to reduce the number of accesses to global memory.
    * Computed the minX, maxX, minY, maxY of the block in float to directly compare with the circle bounding boxes.
    * Added the __restrict__ qualifier to the arrays related to the circles, 
    since they are read-only and accessed by many threads.


    I've also done a simple experiment on circles_checked_per_thread (per round).

    The logic is that there are 256 threads in a block, and each block allocates 
    2 * circles_checked_per_thread * 256 * sizeof(int) bytes of shared memory to store 
    the flag array and the valid_circles array.
    So if we let circles_checked_per_thread = 8, then the shared memory size allocated 
    by a block is 2 * 8 * 256 * 4 = 16 KB.
    Considering the hardware of the RTX 4090, it has 128 SMs, and each SM supports 
    up to 1536 threads and 100 KB of shared memory.
    Recall that the block size we chose uses 256 threads and 16 KB of shared memory, 
    which means an SM can run 6 blocks with high utilization (almost 100% occupancy).

    (Note that a default 1024x1024 image needs 4096 blocks, i.e., about 700 SMs,
    which scales perfectly for the RTX 4090 with its 128 SMs.)

    Notice that if we let circles_checked_per_thread = 16, a block will need 32 KB 
    of shared memory. This means an SM can only run 3 blocks, which is 768 threads 
    (much less than the previous setup). So although it can reduce the total iteration time 
    (reducing the number of __syncthreads calls), it drastically reduces overall efficiency.
    (I put the result of this experiment at the bottom of this file.)
